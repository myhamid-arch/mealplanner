# leaf-1.4.1 ADR-2: jobs (pg-boss 12.34.0), job events and SSE

Status: accepted at CP1 (R-40); as built at CP2
Requirement: ARC-7, ARC-5 (`jobs/:id/events`), PLN-12, FBK-7, KG-3, R2-ADM-8; SPEC-Q-8, SPEC-Q-11

## Decision

- Queue: `pg-boss` **12.34.0** in both apps (the web only sends). One queue per job kind, created by both with the same `QUEUE_OPTIONS` (`policy: "exclusive"`, `retryLimit: 0`, `expireInSeconds: 7200`). A pg-boss job carries `{ jobId }` with `singletonKey` = the `job` row id: at most one pg-boss job per row is queued or active, so re-sends (the tick, a follow-up) are dropped while one is outstanding, and a row sent again after its pg-boss job finished (the redo of an undone `recipe.*` change set) is accepted. pg-boss never retries; the runner retries `kg.*`, `nutrition.recompute` and `plates.resolve` in the same run (after 2 s and 8 s, with a `retrying` event). Plans, AI jobs and the purge fail at once and are re-run only when asked.
- Stale jobs: a job still `running` 2 h 10 min after it started lost its worker; the tick fails it with a terminal `failed` event. The compose file gives the worker a 30 s stop grace (pg-boss stops gracefully within 20 s).
- Enqueue path (`apps/web/lib/server/jobs.ts` `enqueueJob`; the worker's own follow-ups through `WorkerRuntime.enqueue`): insert `job` (`queued`), commit, then `boss.send`. `recipe.generate`/`recipe.revise` rows are inserted by their change ops and sent after the change set commits. A per-minute scheduler tick re-sends rows still `queued` after 30 s (a lost send, or a restart).
- Claim (R-40): `UPDATE job SET status = 'running' WHERE id = $1 AND status = 'queued'`; a withdrawn or already-claimed job is skipped. A `BEFORE DELETE` trigger refuses to delete a job that is no longer queued (`55006`, surfaced as `409 job_started`), so the undo of a `recipe.*` change set and the claim cannot both succeed; only a household purge bypasses it (`mealplanner.purge`). The worker marks `succeeded`/`failed` and writes the error (`failed` rows feed the platform console and diagnostics).
- Events: `job_event (job_id, seq, household_id, type, payload)`; the runner appends `started`, the handler's progress events (for plans, each `PlanProgress`; the planner's own `done` is renamed `planned`), then the terminal `done` (with the job result) or `failed`, each with `pg_notify('job_event', job_id || ':' || seq)` in the same statement. Handlers cannot emit a terminal type (`done`, `failed`, `cancelled`): the stream closes on the first one.
- SSE (`GET /api/v1/jobs/:id/events`): household check on the `job` row (other household → 404); replay rows with `seq > Last-Event-ID`; then `LISTEN job_event` on one shared dedicated `pg.Client` per web process (`apps/web/lib/server/events.ts`, fan-out by job id) and stream new rows; close after the terminal event. `id:` = seq, `event:` = type, `data:` = JSON; a comment heartbeat every 15 s. The stream uses the Web `ReadableStream` returned from the route handler (Next.js App Router streaming, `export const dynamic = "force-dynamic"`, `runtime = "nodejs"`).
- The worker (`apps/worker/src/main.ts`) builds: one `pg.Pool`, Drizzle, `PgBoss`, the Claude client (`resolveClaudeConfig`; null model when no credential), `PostgresGraphStore(pool)` and `PostgresKgSource`, then registers every handler in `apps/worker/src/jobs/*`. Graceful shutdown on SIGTERM (`boss.stop({ graceful: true })`).
- G2 runs the **real worker entry** as a child process (`node apps/worker/dist/src/main.js` against the gate's own database), a real HTTP server around the route handlers, and a `fetch` SSE client; see ADR-3.
